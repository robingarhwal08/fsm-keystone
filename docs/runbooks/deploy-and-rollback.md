## Trigger

- A new image is ready to promote to an environment.
- A post-deploy verification failure requires rollback.
- An alert fires within 15 minutes of a deploy (rollback decision window).

---

## Preconditions

- `.env` and `secrets/` exist on the target host (generated by `bash scripts/dev/bootstrap-secrets.sh`).
- The `POSTGRES_PASSWORD` variable is set in `.env`.
- The migration directory `keystone-backend/src/main/resources/db/migration/` has been reviewed and all new `.sql` files are backward compatible (see Backward-compatibility rule below).
- No active incident is in progress on the target environment.

---

## Backward-compatibility rule

Migrations **must be backward compatible**: the previous application revision and the new application revision must be able to run against the migrated schema simultaneously. This is required because a rolling deploy has both old and new containers coexisting.

**Compliant patterns**: add nullable column, add index, add table, widen a column type.  
**Non-compliant patterns**: rename column, drop column, add NOT NULL without default.  
Non-compliant changes must use the **expand-then-contract** sequence (see [migration-failure.md](migration-failure.md#expand-then-contract)).

## Steps

### 1. Build the backend image

```bash
cd keystone-backend
docker build -t fsm-keystone-backend:${GIT_SHA} .
```

The `Dockerfile` runs `mvn -B clean package -DskipITs=true` — unit and slice tests gate the build; integration tests are skipped inside the builder container.

### 2. Verify the image (optional scan)

```bash
# Example with trivy — substitute your scanner
trivy image fsm-keystone-backend:${GIT_SHA}
```

Fail the pipeline if any CRITICAL vulnerability is found.

### 3. Pre-deploy: run Flyway migration dry-run

```bash
docker compose run --rm backend \
  java -jar app.jar \
  --spring.flyway.dry-run=true \
  2>&1 | tee /tmp/flyway-dry-run.log
```

Inspect `/tmp/flyway-dry-run.log`. If any migration is listed as `PENDING` that is not backward compatible, **stop the deploy** and fix the migration first.

### 4. Apply Flyway migrations

Flyway runs automatically at Spring Boot startup. When the backend container starts, it connects to `postgres-db`, reads `flyway_schema_history`, and applies any pending migrations in version order before the JPA `EntityManagerFactory` initialises.

### 5. Roll the backend container

```bash
docker compose up -d --no-deps --build backend
```

`--no-deps` avoids restarting `postgres-db` and `react-app`.

### 6. Post-deploy verification

```bash
# 1. Container is running
docker compose ps springboot-app

# 2. Application responded to a health probe (basic TCP check until Actuator ships)
curl -sf http://localhost:8080/api/auth/login \
  -H "Content-Type: application/json" \
  -d '{"email":"probe@example.com","password":"noop"}' \
  -w "\nHTTP %{http_code}\n" | grep -E "^HTTP (200|400|401)"

# 3. Flyway history shows the expected applied count
docker compose exec postgres-db \
  psql -U "${POSTGRES_USER:-postgres}" -d "${POSTGRES_DB:-fsmdb}" \
  -c "SELECT version, description, success FROM flyway_schema_history ORDER BY installed_rank;"
```

**Pass criterion**: container running, login endpoint returns 200/400/401, all Flyway rows show `success = true`.

## Rollback Decision Tree

```
Post-deploy verification FAILS?
│
├─ Flyway migration applied? ──── YES ──→ Migration is forward-only.
│                                         Rollback of schema is PROHIBITED.
│                                         Action: roll back the application code only;
│                                         the old revision must tolerate the new schema
│                                         (backward-compatibility rule).
│                                         If old revision cannot start → escalate immediately.
│
└─ Flyway migration NOT applied? ─ NO ──→ Roll back the container image:
                                          docker compose up -d --no-deps backend \
                                            --image fsm-keystone-backend:${PREV_SHA}
```

### Roll back application code (migration already applied)

```bash
# Re-deploy the previous image tag
docker compose stop backend
docker compose up -d --no-deps backend \
  # Set the image tag to the previous known-good SHA
```

> **⚠ Prohibited**: never revert `spring.flyway.clean-disabled=false` or run `flyway clean` as a rollback shortcut. The sanctioned path is fix-forward (see [migration-failure.md](migration-failure.md)).

### Both replicas fail readiness simultaneously

If there is nothing to roll back to (e.g., first deploy, single-container environment):

1. Escalate to Backend / Platform engineer immediately (do not wait 15 minutes).
2. Restore the last known-good database backup (see [database-backup-restore.md](database-backup-restore.md)).
3. Deploy a pinned known-good image tag.

## Escalation

| Condition | Escalate to | Maximum time |
|-----------|-------------|-------------|
| Migration applied, old revision cannot start | Backend / Platform engineer | Immediate |
| Verification still failing 15 min after rollback | Backend engineer + DevOps | 15 minutes |
| Security control disabled during incident attempt | Security reviewer | Immediate |
