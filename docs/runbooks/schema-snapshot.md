# Runbook: Schema Snapshot and Production Dump

**Purpose:** Regenerate `docs/baseline/schema-snapshot.sql` from the live JPA model and/or
capture a schema-only production dump for drift comparison.

**Constraints:** No credentials appear in this runbook. Replace `<placeholder>` values with real
values from your secret store. Do not commit real credentials.

---

## 1. Regenerate the Schema Snapshot Locally

The snapshot is generated by running the JPA model against an ephemeral Testcontainers PostgreSQL 16
instance. Docker must be available on the local machine.

```bash
cd keystone-backend

# Verify the snapshot matches the committed file (read-only):
mvn test -Dtest=SchemaSnapshotTest

# Regenerate and overwrite the committed snapshot (run when entities change):
mvn test -Dtest=SchemaSnapshotTest -Dschema.snapshot.update=true
```

After regeneration, review the diff:

```bash
git diff docs/baseline/schema-snapshot.sql
```

Commit with a message describing the entity change, e.g.:
```
chore(schema): add site.timezone column — regenerate snapshot
```

### Failure: container does not start

If Docker is unavailable or the `postgres:16` image cannot be pulled:

```
Could not find a valid Docker environment
```

**Fix:** start Docker Desktop, or on Linux ensure the Docker daemon is running:
```bash
sudo systemctl start docker
```

If the image is not in the local cache and no internet is available, pre-pull it:
```bash
docker pull postgres:16
```

### Failure: export file not written

If `SchemaSnapshotTest` fails with "Hibernate did not write the schema export file":
1. Check that the `target/` directory exists: `ls keystone-backend/target/`
2. Check that the JPA schema-generation properties are present in `@TestPropertySource`
3. Run `mvn test -Dtest=SchemaSnapshotTest -X` for debug output

## 2. Capture a Schema-Only Production Dump

> **Prerequisite:** operational access to the production PostgreSQL host.
> All connection details are placeholders — retrieve real values from the secret store.

```bash
# Variables (fill from secret store — never commit)
DB_HOST=<production-db-host>
DB_PORT=5432
DB_NAME=fsmdb
DB_USER=<production-db-user>

# Capture schema only (no data rows, no owner clauses, no ACL, no comments)
pg_dump \
  --host="$DB_HOST" \
  --port="$DB_PORT" \
  --username="$DB_USER" \
  --dbname="$DB_NAME" \
  --schema-only \
  --no-owner \
  --no-acl \
  --no-comments \
  --file=production-schema-dump.sql

# Confirm no data rows were captured
grep -c "^INSERT INTO" production-schema-dump.sql || echo "zero INSERT rows — schema-only dump verified"
```

**Do not commit `production-schema-dump.sql` if it contains any data rows or credentials.**
Strip the header comment that `pg_dump` adds (it may include the database name or timestamp):

```bash
# Remove the first pg_dump header comment block
sed '/^--/d' production-schema-dump.sql > production-schema-stripped.sql
```

---

## 3. Diff the Generated Snapshot Against the Production Dump

After obtaining both files:

```bash
# Normalize the production dump the same way the test normalizes the snapshot
# (strip constraint names, lowercase, sort)
# For a quick structural diff, use diff directly — column-presence differences will show up:
diff <(grep -E "^(CREATE TABLE|ALTER TABLE)" docs/baseline/schema-snapshot.sql | sort) \
     <(grep -E "^(CREATE TABLE|ALTER TABLE)" production-schema-stripped.sql   | sort)
```

Record findings (columns in production but not snapshot, or vice versa) in
`docs/baseline/schema-drift-report.md` under "Per-Table Drift Analysis".

---

## 4. Failure Branch: Unreachable Production Database

If the production database is unreachable:

1. Record in `docs/baseline/schema-drift-report.md` under "Production Dump Status" that the
   comparison was performed against the generated baseline only.
2. Note the date and the obstacle (e.g., "no ops access during Phase 0").
3. The drift report remains valid as a partial artifact; complete it when access is available.
4. Set a follow-up ticket for the Flyway epic to complete the comparison before V1 migration.

---

## 5. When to Regenerate

| Trigger | Action |
|---|---|
| A new `@Entity` field is added | Regenerate snapshot; update `entity-column-inventory.md` |
| An existing `@Column` constraint changes (nullable, length, type) | Regenerate snapshot |
| A new `@Entity` class is added | Regenerate snapshot; update inventory and drift report |
| Hibernate version is upgraded | Regenerate snapshot; review for type changes |
| Flyway V1 migration is applied | Regenerate snapshot to confirm `validate` mode passes |
